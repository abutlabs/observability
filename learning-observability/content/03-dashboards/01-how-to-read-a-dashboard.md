# How to read a dashboard

## Every dashboard answers one question

| Folder | Dashboard | uid | The question it answers |
|---|---|---|---|
| platform | Network overview | `obs-overview` | Which nodes make up this net, what client runs each, and is every node keeping up? |
| platform | Chain health | `obs-chain` | Is the net one chain that keeps growing and finalizing, on every node? |
| platform | Logs | `obs-logs` | What did the nodes say? |
| platform | obs self-health | `obs-self` | Is the stack itself collecting? |
| lasair | lasair node overview | `lasair-node` | Is each lasair node healthy right now? |
| lasair | work-package lifecycle | `lasair-wp` | Where does a work-package's time go, and why do packages expire before they are guaranteed? |
| lasair | lasair networking | `lasair-net` | What is lasair saying on the network, how fast do peers answer, and what fails? |
| lasair | lasair PVM | `lasair-pvm` | How fast does lasair's PVM refine work, and for which service? |
| lasair | lasair validator duties | `obs-lasair` | Is every lasair validator doing its whole job? |
| lasair | Memory | `obs-memory` | Does lasair's memory stay bounded as the chain grows? |
| jamswap | DEX | `obs-dex` | Is the DEX turning offered load into cleared trades? |
| jamswap | Soak runs | `obs-soak-runs` | Did this soak pass, and how does it compare with every soak before it? |

The `platform` folder comes from this repository and works for any client. The `lasair`
and `jamswap` folders come from those projects' checkouts. Each dashboard opens with a
short text panel that states its question: read it first.

When you do not know where to start: **obs self-health** (is the stack collecting?), then
**Network overview** (are all nodes there?), **Chain health** (is it one chain?), then the
client and application views.

## The controls at the top

- **net** and **run_id**: every dashboard is scoped to one network and one run. The run
  list shows the newest first (run ids end in their start time). The lasair dashboards add
  **node**, a multi-select of lasair nodes, All by default.
- **Time range**: a live run shows the last hour and refreshes every 10 seconds. For a
  finished run, open the link `./obs link` prints: it sets the net, the run *and* the time
  range in one go. A dashboard showing "no data" for a finished run is usually looking at
  the wrong hour.
- **The obs links**: a row of links to the other dashboards. They keep the variables and
  the time range, so you can move between views of the same run without picking again.

## The panels

**Text** says what the dashboard answers and how to read it.

**Stats** (big numbers) come in two kinds:

- *Pass/fail stats* say what passes in their title: `Head spread · PASS ≤ 3 slots`,
  `Finality conflicts · PASS = 0`. They turn green when the value passes and red when it
  fails. Read the colour, then the number, then check whether the run is live or already
  over: some stats judge a live run and turn red after a planned end (lesson 3.6).
- *Info stats* are grey. They give a figure without judging it, like `Peak RSS, any node
  (info)`.

A stat shows the last value in the time range, so a finished run still shows its final
figure. Stats whose title ends in `(range)` count over the whole time range instead.

**Time series** show how a value moved. Most have one line per node (legend
`node · client`). A dashed red line is a threshold: the dashed line on *Finality lag per
node* is one epoch.

**Tables** give instant values, one row per node.

**Logs panels** list lines from Loki, newest first; click a line to see its labels.

## Annotations

Marks on the time axis of every panel:

- **blue**: a run event (load on, load off, drain, ...);
- **green**: a PASS verdict;
- **red**: a FAIL verdict.

A soak annotates its start, the end of its load, its drain and every verdict line, so you
can see what the network was doing when a check failed.

## Dashboards are code

None of these dashboards is edited in Grafana. Each is JSON kept in git and mounted
read-only, and most are generated by a small Python program:

- the platform dashboards by
  [`dashgen/gen_platform.py`](../../../dashgen/gen_platform.py);
- lasair's four `lasair-*` dashboards by `observability/gen_dashboards.py` in lasair (its
  validator duties and Memory dashboards moved there from jamswap as JSON);
- jamswap's by `observability/gen_dashboards.py` in jamswap.

You can change a panel in Grafana to explore, but Grafana will not save it. To change a
dashboard for good, edit its generator and run it. Each generator has a `--check` mode that
exits 1 if the JSON in git is stale:

```text
$ python3 dashgen/gen_platform.py --check
$ echo $?
0
$ python3 dashgen/gen_platform.py
wrote obs-chain.json, obs-logs.json, obs-overview.json, obs-self.json
```

Grafana picks up the new JSON within 10 seconds.

## When a panel says "no data"

In order of likelihood:

1. **Wrong time range or run.** Open the run's link.
2. **The metric does not exist for this client or build.** The lasair dashboards read
   `jam_*` names that lasair 2.1.2 did not export yet; the platform dashboards need a node
   to report the `jam_*` set through at least one path.
3. **Nothing happened.** A counter that never incremented has no rate. Several pass/fail
   stats add `or vector(0)` so that "never happened" shows as 0 rather than blank.
4. **The stack is not collecting.** Open **obs self-health**.
